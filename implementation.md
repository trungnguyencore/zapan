## 1. Product vision
ZaPan v2 is a Japanese-learning product, not a collection of disconnected quiz modes.
The core loop is: Learn -> Review -> Practice -> Measure -> Adapt.
The default experience should answer: "What should I study next?"
Games are practice surfaces that feed the same learning engine, not separate progress systems.
The initial content target is a reliable N5 foundation; N4/N3 are exposed only when their real content and learning flows exist.

## 2. Non-negotiable engineering rules
1. No green test/evidence -> no progression to the next implementation step.
2. Implemented != Verified != Production-proven.
3. Every learning interaction that affects progress must use one canonical StudyEvent/Progress/SRS model.
4. No duplicated SRS engines or parallel progress schemas.
5. Data migration must be explicit, versioned, testable, and reversible where practical.
6. Accessibility, mobile behavior, dark mode, keyboard use, and failure states are first-class requirements.
7. Documentation must never claim a feature is complete until evidence exists.
8. New architectural/product changes discovered during implementation must be recorded in PROJECT_DECISIONS.md.
9. Significant scope/schema/backend/deployment changes require owner approval before implementation.
10. Existing legacy code may inspire behavior, but no legacy architecture is copied by default.

## 4. Target user experience
Primary navigation:
- Home
- Learn
- Review
- Library
- Progress
Secondary practice tools:
- Writing
- Time Attack
- Survival
- Match
- Confusables
- Custom Practice
Desktop uses an always-available sidebar where space permits.
Mobile uses a bottom navigation for the five primary destinations.

## 5. Home / Today
Home is a daily-learning dashboard rather than a feature launcher.
It should show today's recommended session, due reviews, new-card allowance, weak/slow items, estimated duration, current path, and real activity metrics.

## 6. Learn
Learn is structured by curriculum rather than raw mode selection.
Initial hierarchy: N5 Kana, N5 Vocabulary, N5 Kanji, then later verified Grammar/Reading/Listening modules.
Each topic reports real state: unseen, learning, due, weak, mastered.
Bulk group selection exists only as Custom Practice.

## 7. Review
Review is a dedicated first-class surface.
Initial priority heuristic: overdue -> recently failed -> low accuracy -> slow response -> new reinforcement -> mature scheduled retention.
The algorithm must be deterministic under a seeded clock/random source for tests.
## 8. Unified learning session
Every learning/practice mode must emit canonical study events.
A session has: sessionId, userId/local guest identity, content scope, mode, startedAt/endedAt, StudyEvent entries, and a derived summary.
Modes may change presentation, timing, scoring, or input style, but they do not own separate mastery state.

## 9. Canonical content identity
Every learnable item requires a stable unique cardId that does not depend on display text.
Recommended logical identity: `{level}:{contentType}:{sourceKey}:{itemKey}`.
The concrete format is versioned in code and tests.
Content records carry cardId, level, contentType, prompt/answer data, language metadata, group/topic, and source version.
Content data and user progress are separate domains.

## 10. StudyEvent model
Minimum fields: eventId, sessionId, cardId, mode, result, responseTimeMs when meaningful, occurredAt, inputKind, schemaVersion.
Synthetic or placeholder timing must never be stored as measured response time.

## 11. ProgressRecord model
Minimum fields: cardId, attempts, correctCount, incorrectCount, currentCorrectStreak, accuracy, averageResponseTimeMs, responseTimeSampleCount, lastReviewedAt, nextReviewAt, SRS state, mastery state, updatedAt, schemaVersion.
All screens consume this same record shape.

## 12. SRS direction
ZaPan v2 uses exactly one SRS implementation.
Phase 1 defines a pure deterministic engine with explicit inputs/outputs and unit tests.
The first version may use a conservative interval model rather than pretending to be scientifically optimal.
Any future algorithm change requires an algorithm version, migration decision, regression tests, and a PROJECT_DECISIONS.md entry.
Product heuristics are labeled as heuristics, not research facts.

## 13. Activity tracking
Activity metrics derive from real events/sessions: study minutes, answers/reviews, streak, heatmap, weekly totals.
Streak calculation must define timezone/day-boundary semantics.
No UI may show a tracked metric until the underlying update path is implemented and tested.

## 14. Authentication and backend
Planned backend: Firebase Authentication + Cloud Firestore, subject to implementation verification.
Guest learning remains functional without authentication.
Authenticated users require multi-device sync.
Cloud state must not be selected merely by collection/array length.
Conflict handling is per-record/version/timestamp aware and tested.
Firestore security rules are part of backend implementation. Secrets/private keys are never committed.
## 15. Offline strategy
Core study remains usable when the network is unavailable after required assets/data are present.
Local writes are durable first, then synchronized.
Offline -> online reconciliation must be deterministic and tested.
External dependencies such as stroke-order assets require graceful fallback.

## 16. Frontend architecture
Phase 1 target stack: React, TypeScript, Vite, React Router, design tokens, Vitest + Testing Library, and Playwright.
Exact dependency versions come from the generated lockfile and are evidence, not assumptions.
Target boundaries: `src/app`, `src/features`, `src/domain`, `src/services`, `src/data`, `src/components/ui`.
Cross-feature business logic belongs in domain/services, not page components.

## 17. Design system principles
- Calm visual hierarchy; learning content dominates decoration.
- One primary brand color; domain accents identify Kana/Vocab/Kanji/Review.
- Semantic colors carry consistent meanings.
- Avoid turning every action into a gradient card.
- Practical touch targets about 44 CSS px or larger.
- Visible focus indicators; browser zoom remains enabled.
- Respect reduced-motion preferences.
- Dark/light themes use shared semantic tokens.
- Responsive layout is designed from the start.

## 18. Testing strategy
Testing is continuous, not a final phase.
Every slice gets static/type/lint checks, unit tests for pure logic, component/integration tests at boundaries, manual browser verification for interaction/visual work, regression checks, and recorded evidence.
A failure blocks progression unless explicitly documented as non-blocking.

## 19. GitHub migration
The repository identity/history is preserved.
Do not delete/recreate the repository.
Final migration requires: verify remote/branch, create rollback tag/branch, replace legacy working-tree contents in a reviewed migration, install final README/deploy config, push only after local release gates pass, deploy, smoke-test the live URL, and record deployed commit/evidence.

## 20. Phase 1 exit criteria
Phase 1 completes only when canonical docs are consistent, a greenfield app scaffold exists, local Git state is documented, canonical domain types exist, one deterministic SRS foundation exists, schema/config validation foundation exists, core tests exist, lint/type/build/test gates pass, navigation/design-system skeleton exists, and progress/evidence record actual verification.
